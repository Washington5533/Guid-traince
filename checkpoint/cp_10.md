# cp_10 · MCP 工具层 (mcp_server.py)

**文件**: `guardian/mcp_server.py`
**阶段**: 全程
**核心目标**: 把 guardian 的观测与操作能力暴露为标准 MCP 工具，供 Claude Code / OpenClaw 等外部 agent 客户端接入，实现"服务器上跑训练，任意 agent 客户端都能看/管"

> **架构基线：sidecar-first**（见 [functional_overview.md](functional_overview.md#架构基线sidecar-first)）。sidecar 化让这一层变得更简单：guardian 本身已经在训练进程之外，MCP server 与它同进程（`--with-mcp`）就能直接共享内存里的 monitor/watchdog 状态，**不需要碰训练进程**。三种进程关系：
> - `watch --with-mcp`：MCP server 在 **guardian 进程**内后台线程运行，状态实时共享（注意"同进程"指与 guardian 同进程，不是与训练同进程）
> - `run.py serve` 独立进程：跨进程读盘刷新（`_snapshot_state`），可对着一个已经在跑的 `watch` 补挂
> - 训练子进程：**任何模式下都不感知 MCP 存在**

---

## 为什么需要这一层

cp_9 解决的是"guardian 内部决策点要不要用 agent"，这一层解决的是完全不同的问题：**guardian 之外的 agent（用户在本地跑的 Claude Code、OpenClaw，或任何 MCP 客户端）怎么接入这台服务器上正在跑的训练**。

两者不冲突，可以同时存在，也可以只启用一个：
- 只启用 cp_9：训练本身带一点智能决策，但外部看不到、管不了，只能看日志文件
- 只启用 cp_10：训练还是纯规则引擎，但外部 agent 可以随时查看指标、下达受限指令
- 两者都启用：内部有 agent 决策，外部 agent 还能查看内部决策记录、覆盖决策、下达指令

## 部署形态

```
服务器（训练运行所在机器）
  |
  |- guardian watch 进程
  |     |- cp_2 monitor / cp_3 watchdog / cp_4 analyzer / cp_11 contract
  |     |     `- 持续写入 metrics_history / analysis_report / notifier 日志
  |     |
  |     |- [--with-mcp] MCP server 后台线程：直接共享上述模块的内存状态
  |     |
  |     `- 拉起并看护训练子进程 ─────────┐
  |                                      ▼
  |                          python train.py（0 行 guardian 代码，不感知 MCP）
  |                                产出 wandb/日志、checkpoints/
  |
  `- [或] mcp_server.py 独立进程（run.py serve）
        |- 跨进程定期读盘刷新状态（_snapshot_state）
        `- 可对着一个已在运行的 watch 事后补挂，无需重启训练

本地 / 任意机器
  |
  `- Claude Code / OpenClaw / 其他 MCP 客户端
        `- 通过 SSH 端口转发 或 直连（服务器需开放访问）连上 mcp_server
           查看指标、告警历史、checkpoint 对比；下达受限指令（触发恢复、调整参数重启）
```

服务器场景下推荐 **stdio + SSH 隧道** 或 **本地端口 + 反向代理鉴权**，不建议把 MCP server 直接暴露公网端口（见下方安全说明）。

## 工具清单

### 只读工具（无权限限制，任何连接的客户端都可调用）

| 工具名 | 对应 guardian 能力 | 返回 |
|--------|---------------------|------|
| `get_training_status` | monitor.get_metrics_history() 最新状态 | 当前 epoch/step、最新 loss/acc、GPU 状态 |
| `get_metrics_history` | monitor.get_metrics_history() | 完整指标时间序列（支持 range 参数裁剪） |
| `list_checkpoints` | ckpt_analyzer 扫描 checkpoints/ | 每个 cp 的路径、指标、是否 best/top_k |
| `compare_checkpoints` | ckpt_analyzer.compare_checkpoints(a, b) | 两个 checkpoint 的指标差值 |
| `get_anomaly_history` | monitor 异常事件记录（cp_2） | 全部异常事件 + 应对来源（agent/rule_default） |
| `get_recovery_history` | watchdog 恢复记录（cp_3） | 全部重启事件 + `trigger`（`crash` / `intervention` / `hang`）+ 恢复起点 + 作废 epoch 数 + 结果 |
| `get_summary` | summary.generate() 已生成的摘要 | 结构化摘要 + AI 解读（若有） |
| `get_agent_decision_log` | AgentAdvisor._log_decision 记录（cp_9） | 全部 agent 调用记录，含 source/延迟/降级原因 |
| `get_contract_status` | TaskContract.get_capability_status()（cp_11） | 硬性契约四项各自的开启/降级状态 |
| `list_contract_proposals` | TaskContract.list_proposals()（cp_11） | 全部 agent 提议记录（pending/approved/rejected）+ 依据 |

### 受限写工具（默认关闭，需在配置显式开启并设访问口令）

sidecar 下所有"改参数"类写工具都是**重启式**的（kill + 从 checkpoint 用新参数续训，经 cp_3 统一路径），因此风险描述里必须明说"会作废最近 checkpoint 之后的算力"——外部 agent 需要知道这不是一次免费操作。

| 工具名 | 对应 guardian 能力 | 风险 | 默认状态 |
|--------|---------------------|------|----------|
| `trigger_recovery` | 手动调用 watchdog 重启流程 | 打断训练子进程并回滚到最近 ckpt，作废其后算力 | 关闭 |
| `restart_with_params` | 用调整后的参数重启训练（batch_size / lr 等，受 cp_11 白名单与 `cli_mappings` 约束） | 同上；参数越界会被 `_validate_action` 拒绝 | 关闭 |
| `stop_training` | 停止训练子进程并终止看护 | 训练中止，需人工重新拉起 | 关闭 |
| `override_agent_decision` | 覆盖 AgentAdvisor 下一次决策的默认动作 | 绕过规则引擎兜底 | 关闭 |
| `trigger_full_validate` | 手动触发指定 checkpoint 的完整校验 | 占用算力，可能与训练争抢 GPU | 关闭 |
| `approve_contract_proposal` | 批准一条 cp_11 的 agent 提议，写入正式注册表/白名单 | 扩大 agent 后续可自主选择的空间 | 关闭 |
| `reject_contract_proposal` | 拒绝并归档一条 cp_11 的 agent 提议 | 无（纯拒绝操作），仍需鉴权避免误操作 | 关闭 |

原设计里的 `adjust_batch_size`（运行时热改）和 `pause_training` / `resume_training`（暂停主循环）**在 sidecar 下不成立**——进程外既不能改另一个进程的 dataloader，也不能挂起它的训练循环而不影响 GPU 占用。前者由 `restart_with_params` 取代，后者收敛为 `stop_training`。两者在嵌入模式下仍可注册。

写工具的调用统一经过 `_authorize(tool_name, token)` 校验，未授权直接拒绝并返回明确错误（不是静默失败）。所有写调用无论成功失败都记入 `mcp_access_log.json`，包含调用方标识（客户端提供的 client_id）、时间、参数、结果。

## 关键类与方法

### `GuardianMCPServer`

| 方法 | 说明 |
|------|------|
| `__init__(config, monitor, ckpt_analyzer, watchdog, summary_gen, advisor, task_contract)` | 绑定 guardian 进程内各模块实例（`--with-mcp` 共享内存状态）或指定读取路径（`run.py serve` 跨进程定期读盘） |
| `start(transport="stdio")` | 启动 MCP server，transport 支持 `stdio` / `tcp` |
| `start_in_background(transport="stdio")` | `--with-mcp` 专用：在 guardian 进程内的独立线程启动，绝不阻塞 guardian 的看护循环，更不触及训练子进程，详见下方"非阻塞保证" |
| `register_readonly_tools()` | 注册全部只读工具 |
| `register_write_tools()` | 注册受限写工具（仅当 config.mcp.enable_write_tools 为真时调用） |

| `_snapshot_state()` | 跨进程模式下，定期从磁盘（metrics_history.json / analysis_report.json 等）刷新内存快照 |
| `_log_access(tool_name, client_id, params, result, success)` | 记录一次工具调用到 mcp_access_log.json |

## 非阻塞保证（轻量部署 + MCP 叠加共存的前提）

`mcp` 属于可选的 `requirements-mcp.txt`（详见 [requirements.md](requirements.md)），训练本身和 cp_9 的 agent 决策层完全不依赖它。这一层存在的前提是：**MCP 无论以什么方式启动、以什么方式失败，都不能反向影响训练**。具体到实现上是三条硬性约束：

1. **`mcp` 包未安装** → `import mcp` 失败时 `--with-mcp` / `run.py serve` 只打印一条说明（提示装 `requirements-mcp.txt`），`--with-mcp` 场景下 `guardian watch` 照常以非 MCP 模式继续守护训练，不抛异常、不退出
2. **端口/资源绑定失败**（如 `tcp_port` 被占用）→ `start_in_background()` 捕获异常，记一条 warning 到日志，guardian 的看护循环与训练子进程都不受影响；`run.py serve` 独立进程场景下则该次 serve 直接退出，不影响任何已在运行的 watch 或训练进程
3. **MCP server 运行时崩溃** → 只影响"外部 agent 看不到/管不了这次训练"，不会传导到 guardian 看护逻辑，更不会传导到训练子进程；`start_in_background` 所在线程的异常必须被隔离捕获，不能冒泡到 watch 主循环

**sidecar 架构让这三条更容易成立**：MCP server 与训练之间隔了两层（MCP 线程 → guardian 进程 → 训练子进程），训练子进程从不感知 MCP 是否存在。即使整个 guardian 进程被杀掉，训练子进程也只是失去看护、继续自己跑完（不会被连带杀死——`watch` 应把训练子进程与自身的生命周期解耦，或在退出时明确选择"留下训练继续跑"而非默认 kill）。

这几条保证了"轻量快速远程部署"和"随时叠加 MCP 接入"可以在同一次部署里自由组合，MCP 出问题的上限永远是"这次不可被外部接入"，不会变成"训练受影响"。

## 配置示例

```yaml
mcp:
  enabled: true
  transport: stdio            # stdio / tcp
  tcp_port: 8765               # transport=tcp 时生效，仅绑定 127.0.0.1，配合 SSH 隧道使用
  enable_write_tools: false    # 默认关闭受限写工具
  write_token_env: GUARDIAN_MCP_TOKEN   # 写工具访问口令从环境变量读取
  state_refresh_interval: 5    # 跨进程模式下的状态刷新间隔（秒）
```

## 安全说明

- **默认不做鉴权的是只读工具**，因为读取训练指标本身风险很低；写工具默认关闭且强制口令校验，避免任何连上来的客户端都能打断训练或改参数。
- **不建议直接绑定公网 0.0.0.0 端口**。`transport: tcp` 默认只绑定 `127.0.0.1`，远程访问要求用户自行走 SSH 端口转发（`ssh -L 8765:127.0.0.1:8765 user@server`）或反向代理加鉴权层，MCP server 本身不做公网层面的额外加固。
- **写工具的 token 走环境变量**，不写入配置文件或日志，`mcp_access_log.json` 记录调用但不记录 token 本身。
- **override_agent_decision 是风险最高的工具**，它直接绕开了 cp_9 的规则兜底，务必在文档里显著标注，且建议仅在人工临时介入排障时短暂开启。
- **approve_contract_proposal 的风险类似**：它扩大了 agent 后续可自主选择的指标/路径空间，一旦批准就对后续所有同类任务生效，建议连同 `evidence` 字段一起审阅，而不是只看提议的名字就批准。
- **重启式写工具的代价要在工具描述里写明**：`trigger_recovery` / `restart_with_params` 会作废最近 checkpoint 之后的全部算力。外部 agent（Claude Code 等）只能从工具描述判断代价，因此 `description` 里必须包含"此操作会回滚到最近 checkpoint，可能作废数个 epoch 的训练"，而不是只写"重启训练"。

## 面向 agent 的工具设计要求

这一层的消费者是 LLM，不是人。除了上面的权限分级，还有五条针对 agent 的设计约束：

1. **用 MCP 原生 annotations 表达风险分级**，而不是只写在文档里。`readOnlyHint` / `destructiveHint` / `idempotentHint` 让客户端（Claude Code）自动决定是否需要额外确认——`get_training_status` 标 `readOnlyHint=true` 完全不必打扰用户，`trigger_recovery` 标 `destructiveHint=true` 则单独确认一次。

| 工具类别 | readOnlyHint | destructiveHint | idempotentHint |
|----------|--------------|-----------------|----------------|
| `get_*` / `list_*` / `compare_*` | true | false | true |
| `trigger_full_validate` | false | false | true（重复调用只是重算，结果相同） |
| `restart_with_params` / `trigger_recovery` | false | **true** | false（每次调用都作废一段算力） |
| `stop_training` | false | **true** | true（已停止时重复调用无副作用） |
| `approve_contract_proposal` / `reject_contract_proposal` | false | false | true（同一 proposal 重复审批无额外效果） |

2. **description 写给模型看，不是写给人看**：每个工具必须说明参数格式、取值范围、一个典型调用示例。`get_metrics_history` 的 `range` 参数长什么样，不写清楚 agent 只能猜。

3. **大结果集必须分页/裁剪**。训练几十万 step，`get_metrics_history` 全量返回会直接塞爆 agent 的上下文。默认只返回"最近 N 条 + 聚合统计"，完整序列要显式传 `limit` / `cursor` 分页拉取。这是 agent 工具设计的硬要求，不是优化项。

4. **静态数据用 MCP resources 而非 tools**。已生成的 `summary` / `analysis_report.json` 这类读一次基本不变的内容，作为 resource 暴露可以让客户端直接当上下文引用，省掉一次工具调用往返。变化的实时状态（training_status、metrics）仍然用 tools。

5. **写工具必须定义幂等语义**。agent 会在超时/网络抖动后重试同一调用——`restart_with_params` 被连续调用两次是排队重启两次、还是识别为重复请求？本设计的约定：写工具接受可选的 `request_id`，相同 `request_id` 在 5 分钟内重复到达时直接返回首次结果而不再执行，并在 `mcp_access_log.json` 标记 `deduplicated: true`。这是"给 agent 用"和"给人用的 CLI"最关键的差异之一。

```bash
# 方式一：项目级 .mcp.json（随仓库走，团队共享）
cat > .mcp.json <<'EOF'
{
  "mcpServers": {
    "guardian": {
      "command": "python",
      "args": ["-m", "guardian.mcp_server", "--transport", "stdio"]
    }
  }
}
EOF

# 方式二：CLI 注册
claude mcp add guardian -- python -m guardian.mcp_server --transport stdio
```

## ✅ 完整校验

| 检查项 | 验证方式 | 通过标准 |
|--------|----------|----------|
| 跨进程状态同步 | `run.py serve` 独立进程 vs `guardian watch` 进程 | state_refresh_interval 内指标保持同步 |
| 并发多客户端 | 2 个 MCP 客户端同时连接读取 | 互不阻塞，数据一致 |
| 写工具生效 | 授权后调用 `restart_with_params(batch_size=32)` | 训练子进程被重启，新进程实际使用 batch_size=32，且记录一条 `trigger=intervention` 的重启 |
| 写工具幂等 | 同一 `request_id` 连续调用 `restart_with_params` 两次 | 只重启一次，第二次返回首次结果并在访问日志标记 `deduplicated: true` |
| 越界参数被拒 | `restart_with_params(lr=1.0)`，超出 cp_11 白名单 `max_delta_ratio` | 返回明确错误，不重启训练 |
| 大结果集裁剪 | 训练 10 万 step 后不带参数调用 `get_metrics_history` | 返回最近 N 条 + 聚合统计，而非全量序列 |
| 分页拉取 | 传 `limit` / `cursor` 连续拉取 | 能完整遍历历史，无重复无遗漏 |
| override 与规则兜底 | override_agent_decision 后立即触发一次决策 | 使用覆盖后的动作，而非规则默认值 |
| 访问日志完整 | 连续 10 次读写调用 | mcp_access_log.json 全部记录，含成功和失败 |
| 长连接稳定性 | 客户端保持连接 1 小时，训练持续进行 | 无内存泄漏，工具响应延迟稳定 |
| OpenClaw 接入 | 按 OpenClaw MCP 客户端配置连接 | 能正常调用只读工具，行为与 Claude Code 一致 |
| SSH 隧道场景 | tcp transport + SSH 端口转发 | 本地客户端通过隧道正常访问，直连公网端口失败（未转发时不可达） |
| MCP 崩溃不影响训练 | 训练中强杀 MCP server 线程/进程 | guardian 继续看护、训练子进程继续跑，仅外部接入不可用 |
| guardian 退出不连带杀训练 | `guardian watch` 运行中 Ctrl-C | 按配置选择"留下训练继续跑"或明确提示将 kill，不静默连带杀死训练子进程 |
| 端口冲突不影响训练 | `--with-mcp` 时 tcp_port 已被占用 | 训练照常运行，日志记录一条 MCP 启动失败的 warning |
| 事后补挂不中断训练 | 训练以 `train --agent`（不带 `--with-mcp`）运行一段时间后，另起 `run.py serve` | 无需重启训练进程即可通过 MCP 查询到实时状态 |
