# cp_11 · 任务契约与自适应层 (TaskContract)

**文件**: `guardian/task_contract.py`
**阶段**: 全程（训练前声明与校验，训练中/训练后被 cp_1 / cp_2 / cp_3 / cp_4 / cp_9 引用）
**核心目标**: 把"训练脚本必须提供什么""agent 可以在哪些指标/路径里做任务相关的选择"收敛为一份显式契约——边界由工程师定义，边界内的具体选择交给 agent 按任务自适应，agent 想突破边界必须先提议、经人工审核才生效

> **架构基线：sidecar-first**（见 [functional_overview.md](functional_overview.md#架构基线sidecar-first)）。本模块是 sidecar 形态得以成立的前提：guardian 在训练进程之外，**看不见任何进程内变量**，只能依赖这份契约声明的四个外部可见接口（可续训入口、checkpoint 文件格式、指标输出通道、可 import 的构造函数）。因此契约里的"硬性四项"不是最佳实践建议，而是 sidecar 能否工作的硬边界。

---

## 为什么需要这一层

上一轮讨论"训练脚本非侵入性"时发现两类隐性假设一直没有显式化：训练脚本要"可续训"、指标要"可被外部观测"，否则对应能力会静默失效但不易定位原因。同时 cp_4 的 best-model 判定、cp_2/cp_3 的应对/恢复策略调整，都隐含着"这次任务该用什么口径衡量好坏""这次任务能调哪些参数"这类判断——如果每个项目手写死，agent 没有跨任务复用的空间；如果完全交给 agent 自由发挥，又破坏了"agent 只能在预定义空间内选择"这条已经在 cp_9 里立住的安全不变式。

`TaskContract` 把这两类问题统一成同一种模式：

- **注册表 / 白名单划边界**——人定，不接受 agent 单方面修改
- **agent 在边界内做任务相关的具体选择**——select_metric / select_adjust_path，走 cp_9 的 `decide()` 同一套超时/降级契约
- **agent 想扩边界**——只能生成"提议"，不生效，人工审核通过后才写入正式注册表

这样"公约"本身是双方认可、任何一方不能单方面突破的规则，agent 的智能体现在"边界内怎么选"和"边界不够时怎么提议"，而不是"边界该是什么"。

## 关键类与方法

### `TaskContract`

| 方法 | 说明 |
|------|------|
| `__init__(config, contract_path)` | 加载 `configs/contract.yaml`（或工程师指定路径），解析训练脚本声明的契约项 |
| `validate_script_contract()` | 校验训练脚本是否满足硬性契约四项，逐项返回满足/降级状态。sidecar 下全部靠外部可见证据判定：`--help` 输出是否含 resume 参数、checkpoint 文件是否含必需键、指标通道路径是否存在且在增长、构造函数入口能否 import |
| `get_capability_status()` | 返回四项能力各自的开启/降级状态，供 `guardian watch` 启动时打印，供 MCP 只读工具查询 |
| `select_metric(task_context)` | 从指标注册表里，结合任务线索选出本次训练的"最优模型判定指标"；经 `AgentAdvisor.decide()`，未启用/失败时回退 `_fallback`（val_loss）。sidecar 下 `task_context` 只含外部可得线索（见下方"推断依据"） |
| `select_adjust_path(decision_point, context)` | 从可调路径白名单里，结合当前决策点选出允许调整的具体路径与幅度；经 `AgentAdvisor.decide()`，未启用/失败时回退该决策点原有的规则默认动作（与改动前行为一致）。sidecar 下只返回能映射到训练脚本命令行参数的路径 |
| `_resolve_cli_mapping(path)` | 把白名单里的抽象路径（如 `optimizer.lr`）解析为训练脚本的实际命令行参数（如 `--lr`）；解析失败的路径在 sidecar 模式下不注册进 action_space |
| `propose_registry_entry(kind, draft_entry, evidence)` | agent 在指标注册表/白名单里找不到匹配任务的条目时，生成一条"建议新增"记录（不生效），写入 `contract_proposals.json`，status="pending" |
| `approve_proposal(proposal_id)` / `reject_proposal(proposal_id)` | 人工审核入口（CLI `run.py contract review` 或 MCP 写工具），approve 后才写入正式 `metric_registry` / `adjustable_paths` |
| `list_proposals(status=None)` | 列出待审核/已处理的提议，供 CLI 和 MCP 只读工具查询 |

## 契约结构

### 1. 硬性契约（训练脚本必需内容，人定死，agent 不可修改）

这四项是 sidecar 与训练进程之间唯一的接口面——guardian 能做什么，完全取决于这四项声明了什么。

```yaml
# configs/contract.yaml
script_contract:
  resumable:
    entry: "cli"                      # cli | function（sidecar 模式必须为 cli）
    resume_flag: "--resume"
    ckpt_flag: "--ckpt"
  checkpoint_schema:
    required_keys: [epoch, model_state_dict, optimizer_state_dict]
    recommended_keys: [rng_state]      # 缺失不阻断，仅在完整校验里提示
  metrics_channel:
    type: wandb                        # wandb | tensorboard | log_file | metrics_json
    path: "./wandb"
    log_pattern: null                  # type=log_file 时必填，如 "step (\\d+) loss ([\\d.]+)"
  buildable_entry:
    model_fn: "train:build_model"
    dataloader_fn: "train:get_dataloaders"
  cli_mappings:                        # 可调路径 → 训练脚本命令行参数（sidecar 重启式干预的传参依据）
    optimizer.lr: "--lr"
    dataloader.batch_size: "--batch_size"
    dataloader.num_workers: "--num_workers"
    # 未声明映射的路径，在 sidecar 模式下不可调
  launcher: "python"                   # python | torchrun | accelerate（影响能否安全调整 batch）
  batch_semantics: null                # per_gpu | global | null(未声明)
                                       # torchrun 等多进程启动下未声明时，v0 不调整 batch，只原样重启
  strict_mode: false                   # true 时任一必需项缺失直接阻止启动
```

`validate_script_contract()` 逐项检查，**缺失某一项只关闭该项对应的能力，不影响其余功能**（与 cp_9"未配置 agent 自动降级为纯规则"是同一套哲学）：

| 缺失项 | sidecar 下关闭的能力 | 仍可用 |
|--------|----------------------|--------|
| `resumable` | 自动恢复 + **全部重启式干预**（cp_3 整个执行路径失效，cp_2 只剩 `alert_only`） | 监控/告警/checkpoint 分析照常 |
| `checkpoint_schema` 必需键不全 | 该 checkpoint 的续训/断点分析 | 其余 checkpoint 不受影响 |
| `metrics_channel` | loss 级异常检测（退化为进程级看护：存活 + GPU） | 硬件监控、崩溃恢复照常 |
| `buildable_entry` | `run.py preflight` / `run.py analyze` | 守护、监控、恢复全部照常 |
| `cli_mappings` 为空 | 带参数调整的重启式干预（`restart_with_lower_lr` / `reduce_batch`），只剩 `resume_unchanged` / `rollback_to_last_ckpt` | 原样重启的恢复照常 |
| `launcher: torchrun` 且 `batch_semantics` 未声明 | batch_size 相关的调整动作（语义不明，不猜） | lr 调整、原样重启、全部监控能力照常 |

注意 `resumable` 在 sidecar 下的权重远高于嵌入模式：**它不只关闭"崩溃恢复"，而是关闭了 sidecar 唯一的干预手段**——不能重启就只能告警。这是 sidecar-first 架构下最关键的一条契约。

`strict_mode: true` 时任一必需项缺失，`guardian watch` 启动前直接报错退出并打印缺失清单，不静默降级——供对契约完整性要求高的团队使用。

### 2. 指标注册表（软性，agent 在其中选择）

```yaml
metric_registry:
  classification:
    - {name: accuracy, direction: max}
    - {name: f1_macro, direction: max}
  detection:
    - {name: mAP50, direction: max}
  segmentation:
    - {name: mIoU, direction: max}
  regression:
    - {name: rmse, direction: min}
  _fallback: {name: val_loss, direction: min}
```

`select_metric()` 推断顺序：config 里显式的 `task_type`（有则直接用对应分组）→ 未声明则交给 agent 从下方"推断依据"里的线索判断任务类型 → 推断/调用失败一律回退 `_fallback`。**agent 只能从已注册的指标里选，不能现场发明指标的计算逻辑**；选择结果（含来源：`config_explicit` / `agent_inferred` / `fallback`）记入 analysis_report.json，供复盘"这次为什么用 mAP 不用 accuracy"。

#### 推断依据（sidecar 下只有外部可得线索）

guardian 在训练进程外，**拿不到 loss 函数对象、模型输出 shape、label 张量结构**。可用线索只有：

| 线索来源 | 具体内容 | 可得性 |
|----------|----------|--------|
| 指标通道里的键名 | wandb/tensorboard 已记录的 `val/mAP50`、`val/mIoU`、`train/dice_loss` 等键名 | **最强线索**——脚本自己记了什么指标，基本就说明了任务类型 |
| checkpoint 文件 | `metrics.json` 里的字段名；`model_state_dict` 最后一层的 shape（可从 state_dict 读出类别数） | 强 |
| 日志文本 | 训练脚本打印的行（可能含 "mAP"、"IoU"、"num_classes=80"） | 中 |
| config 声明 | `task_type` 显式声明 | 最强，但需人工写 |
| `buildable_entry` | 若声明了可 import 入口，可在**独立进程**里 import 后检查模型输出层与 loss 定义 | 强，但要求该契约项存在，且只能在训练前做一次 |

**这比嵌入模式弱，但对 select_metric 这个决策点够用**：一个记录了 `val/mAP50` 的 run 几乎不可能是分类任务。推断不出来时回退 `val_loss`，代价只是 `best.pth` 用了通用口径，可事后用 `run.py analyze --metric mAP50` 重算，不影响训练本身。

### 3. 可调路径白名单（软性，agent 在其中选择 + 定幅度）

```yaml
adjustable_paths:
  - path: "optimizer.lr"
    max_delta_ratio: 0.5        # 单次最多调整 ±50%
  - path: "dataloader.batch_size"
    min_value: 8
    max_delta_ratio: 0.5
  - path: "scheduler.warmup_steps"
    max_delta_ratio: 0.3
```

cp_2 / cp_3 原有的"有限动作集"（`restart_with_lower_lr(ratio)`、`reduce_batch(ratio)` 等）底层改为查询这份白名单+范围，而不是各模块各自硬编码；**对外行为不变**，只是"哪些路径可调、调多大"从散落定义收敛到一处，且可以跨任务复用。agent 建议的幅度超出 `max_delta_ratio` / 低于 `min_value` 时，视为非法输出，复用 cp_9 `_validate_action()` 的校验逻辑回退规则默认动作。

**sidecar 下多一道过滤：路径必须能映射到命令行参数。** `select_adjust_path()` 组装 action_space 时，对每条白名单路径调用 `_resolve_cli_mapping(path)`，在 `script_contract.cli_mappings` 里查不到映射的路径直接**不注册**——agent 看不到就不会选，不存在"选了一个进程外没法生效的动作"。

```
白名单声明 optimizer.lr / dataloader.batch_size / scheduler.warmup_steps
cli_mappings 只声明了 optimizer.lr → --lr, dataloader.batch_size → --batch_size
  │
  └─ sidecar action_space 只含 optimizer.lr、dataloader.batch_size
     scheduler.warmup_steps 被静默过滤（日志记录一条"路径不可达"说明）
     嵌入模式下三条都在（进程内可直接改 scheduler 对象）
```

这也意味着**同一份白名单在两种模式下产生不同大小的动作空间**，但安全不变式一致：agent 永远只能从"已注册且实际可执行"的动作里选。

### 4. Agent 提议扩展（受控，需人工审核）

```
select_metric() / select_adjust_path() 在现有注册表/白名单里找不到匹配当前任务的条目
  │
  └─ propose_registry_entry(kind, draft_entry, evidence)
       ├─ 写入 contract_proposals.json，status="pending"（不生效）
       ├─ 当次决策仍然回退 `_fallback` / 该决策点原有规则默认动作
       │   —— 不会因为"注册表里没有"就卡住，也不会用未经审核的条目
       └─ 人工审核：CLI `run.py contract review` 或 MCP 写工具
            ├─ approve_proposal() → 写入正式 metric_registry / adjustable_paths，后续任务可直接复用，不用每次重新推断
            └─ reject_proposal()  → 归档，记录拒绝理由，避免同类提议反复出现
```

`draft_entry` 必须附带 `evidence`（agent 推断依据），供人工审核时判断是否合理，而不是只给一个名字。sidecar 下 evidence 只能引用外部可得线索，例如："指标通道里出现 `val/dice`、`val/hausdorff` 两个键，checkpoint 最后一层输出 2 通道，判断为分割任务，注册表 segmentation 分组缺少 dice"。**evidence 里不应出现"loss 函数是 XXX"这类进程内信息**——sidecar 拿不到，出现即说明推断链路有问题。

## 与既有模块的关系

| 模块 | 变化 |
|------|------|
| cp_1（资源预估） | `_recommend_batch_size` 参考 `adjustable_paths` 里 `dataloader.batch_size` 的范围与下限，推荐值不超出白名单约束；本身依赖 `buildable_entry` 契约项才能运行 |
| cp_2 | 动作集来源改为查询 `adjustable_paths` + `cli_mappings` 过滤；sidecar 下 `skip_batch`/`lower_lr` 不注册，只有重启式动作 |
| cp_3 | 重启时的传参依据来自 `cli_mappings`；`resumable` 契约缺失时整个重启式执行路径关闭 |
| cp_4（断点分析） | `update_best()` 使用的判定指标不再来自配置里手写的 `monitor_metric`，改由 `TaskContract.select_metric()` 给出；`analysis_report.json` 新增 `metric_source` 字段 |
| cp_9（AgentAdvisor） | 新增两个 decision_point：`select_metric`、`select_adjust_path`，走既有 `decide()` 契约；`propose_registry_entry` 不经过 `decide()`（不需要超时/降级语义，本身就是"不生效的建议"），走独立的只读式 `advisor.suggest()` |
| cp_10（MCP） | 新增只读工具 `get_contract_status`（能力开启/降级状态）、`list_contract_proposals`；新增受限写工具 `approve_contract_proposal` / `reject_contract_proposal`（默认关闭，同其余写工具走 `_authorize`） |

## ✅ 快速校验

| 检查项 | 验证方式 | 预期结果 |
|--------|----------|----------|
| 契约加载 | `TaskContract(config, "configs/contract.yaml")` | 无异常 |
| 硬性契约校验 | 缺失 `resumable` 声明 | `get_capability_status()` 中 resumable=False，其余不受影响 |
| 契约检查命令 | `run.py contract check` | 逐项打印四项契约的通过/降级状态与判定依据 |
| 指标选择降级 | advisor 未启用 | `select_metric()` 返回 `val_loss`，来源标注 `fallback` |
| 路径选择降级 | advisor 未启用，OOM 触发 | `select_adjust_path` 返回原规则默认动作（`reduce_batch(0.5)`） |
| CLI 映射过滤 | 白名单含 `scheduler.warmup_steps`，`cli_mappings` 未声明它 | sidecar action_space 不含该路径，日志记录"路径不可达" |
| 提议写入 | 调用 `propose_registry_entry` | `contract_proposals.json` 出现一条 `status="pending"` 记录，注册表本身不变 |

## ✅ 完整校验

| 检查项 | 验证方式 | 通过标准 |
|--------|----------|----------|
| 任务类型推断（键名线索） | 指标通道里只有 `val/accuracy`、`train/loss` | `select_metric` 返回 accuracy 或 f1_macro，来源记录为 `agent_inferred` |
| 任务类型推断（检测任务） | 指标通道里出现 `val/mAP50` | 返回 mAP50，不误判为分类任务 |
| 仅靠 checkpoint 推断 | 无指标通道，只有 checkpoints/ 目录 | 能从 `metrics.json` 字段名 + 输出层 shape 得出结论，或明确回退 `val_loss` |
| 未知任务类型 | 线索指向注册表未覆盖的任务 | 触发 `propose_registry_entry`，当次仍回退 `val_loss` |
| evidence 不含进程内信息 | 检查生成的 proposal | `evidence` 只引用指标键名/文件字段/日志文本，不含"loss 函数对象"这类 sidecar 拿不到的内容 |
| 白名单边界生效 | agent 建议 lr 调整超过 `max_delta_ratio` | 视为非法输出，回退规则默认动作 |
| 审核通过生效 | `approve_proposal(id)` | 正式注册表新增该条目，后续同类任务无需再次 agent 推断即可命中 |
| 审核拒绝归档 | `reject_proposal(id)` | `contract_proposals.json` 标记 `status="rejected"` 并记录理由，不重复提议同一内容 |
| 严格模式阻断 | `strict_mode: true` 且契约缺失 | `guardian watch` 启动前阻止，打印缺失项清单 |
| 与 cp_4 集成 | best-model 判定实际调用 `select_metric` | `analysis_report.json` 记录本次使用指标及 `metric_source` |
| 与 cp_2/3 集成 | OOM 场景下收紧 `adjustable_paths` 中 batch_size 范围 | agent 建议值超出范围时被拒绝，回退默认 |
| resumable 缺失的连带影响 | 契约未声明 `resumable`，触发一次 loss_spike | cp_2 动作集只剩 `alert_only`，不尝试任何重启式干预 |
| cli_mappings 为空 | 清空 `cli_mappings`，触发 OOM | 只能 `resume_unchanged`，`reduce_batch` 不在 action_space 内 |
| agent_can_propose=false | 找不到匹配条目 | 直接回退，不生成 `contract_proposals.json` 记录 |
