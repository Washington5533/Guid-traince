# cp_12 · 故障注入测试装置 (faultbench)

**文件**: `tests/faultbench/` + `tests/faultbench/fake_train.py`
**阶段**: 测试（不参与生产运行）
**核心目标**: 让 v0 的验收标准可被真实执行——**OOM 能救回来、`kill -9` 能续训、代码错误不被反复重启**。这些是本项目存在的理由，但用 MNIST 一条都验证不了。

---

## 为什么需要这一层

[cp_7.md](cp_7.md) 的 SimpleCNN 约 60 万参数、CPU 数分钟跑完：**永远不会 OOM、不会把 GPU 烤到告警阈值、不会跑够时长触发多轮恢复**。而 cp_2 / cp_3 的完整校验里写着"初始 64，OOM 后恢复时 batch_size=32"、"GPU 温度过高"、"连续 3 次 OOM 前两次均失败"这类检查项——**跑通 MNIST 不构成对它们的任何证据**。

没有这一层，v0 的验收只能靠"看起来没报错"。faultbench 的作用是把每一条故障路径变成一个可重复、秒级、不需要真 GPU 的测试用例。

设计原则：**故障来自被守护的脚本和环境，不来自 guardian 内部的 mock。** guardian 走的是完整的真实代码路径（真的拉子进程、真的读退出码、真的改写命令行、真的重启），只有"故障"本身是人为制造的。这样测出来的才是 guardian 的行为，而不是 mock 的行为。

---

## 组成

### 1. `fake_train.py` — 可编程失败的假训练脚本

一个满足 [cp_11.md](cp_11.md) 契约四项、但**行为完全可控**的训练脚本：接受与真实脚本相同的命令行参数（`--resume` / `--ckpt` / `--lr` / `--batch_size` / `--epochs`），照常写 checkpoint 和指标日志，但可以被指令化地在指定时机以指定方式失败。

```bash
# 在 epoch 3 打印 CUDA OOM 报错并以非零码退出
python fake_train.py --epochs 10 --fail-at 3 --fail-mode oom

# 在 epoch 3 抛 TypeError（不可恢复）
python fake_train.py --epochs 10 --fail-at 3 --fail-mode type_error

# 只有当 batch_size > 16 时才 OOM——用于验证"减 batch 后真的能救回来"
python fake_train.py --epochs 10 --fail-mode oom_if_batch_gt --fail-threshold 16

# 正常跑完，但 loss 在 epoch 4 突增 50%（触发 cp_2 检测）
python fake_train.py --epochs 10 --loss-spike-at 4 --loss-spike-ratio 0.5

# 输出 NaN loss
python fake_train.py --epochs 10 --nan-at 5

# 挂起不退出（验证无进展检测 / 超时看护）
python fake_train.py --hang-at 3
```

关键设计：`--fail-mode oom_if_batch_gt` 这一类**条件失败**是整个装置里最重要的部分。它让"救回来"这件事可被验证——guardian 减半 batch 后脚本不再失败并跑完，才算真的救回来了；只测"OOM 后有没有重启"是不够的，重启后继续 OOM 也叫重启了。

`fake_train.py` 必须**真的**写出符合契约的 checkpoint（含 `epoch` / `model_state_dict` / `optimizer_state_dict`，用极小的张量即可）和真的往日志/metrics.json 写指标，否则 cp_4 的发现与校验、cp_3 的 `_find_latest_checkpoint` 都测不到真实路径。

### 2. 环境层故障（不需要脚本配合）

| 故障 | 制造方式 | 验证的模块 |
|------|----------|------------|
| 进程被 SIGKILL | 外部 `kill -9 <pid>`，或 `fake_train.py --self-kill-at N` | cp_3 退出码 137/-9 识别 |
| cgroup OOM-killer | 在容器内设内存上限后让脚本申请超量内存 | cp_3 OOM-kill 识别（与 CUDA OOM 路径不同） |
| GPU 高温 / 空转 | mock `nvidia-smi` 输出（PATH 前置一个假的 nvidia-smi 脚本，或注入 `GUARDIAN_FAKE_NVIDIA_SMI` 指向固定输出） | cp_2 `gpu_temp` / `gpu_idle` 检测 |
| checkpoint 损坏 | 写入后截断文件 / 写入空文件 | cp_3 `_find_latest_checkpoint` 跳过损坏项、cp_4 容错 |
| 半截 checkpoint | 写入过程中暂停（`--slow-ckpt-write`），让 guardian 恰好在写入中轮询 | cp_4 并发安全判据 |
| 磁盘写满 | 写入到一个受限大小的 tmpfs | cp_4 保存失败容错 |
| LLM 不可用 | 指向一个必定超时/报错的假 endpoint | cp_9 超时降级、熔断 |

**mock nvidia-smi 是这里的关键技巧**：GPU 温度/利用率类告警在任何没有真实高温 GPU 的机器上都无法验证，而通过 PATH 前置一个输出固定文本的假 `nvidia-smi`，cp_2 的采集与检测走的仍是完整真实路径。

### 3. 场景用例（端到端，对应 v0 验收标准）

每个场景是一次完整的 `guardian watch` 运行，断言最终状态与重启轨迹：

| 场景 | 命令 | 通过标准 |
|------|------|----------|
| **S1 OOM 救回** | `watch -- python fake_train.py --epochs 10 --fail-mode oom_if_batch_gt --fail-threshold 16 --batch_size 64` | 经若干次重启后 batch 降至 16 以下，训练**跑完 10 epoch**；摘要 `restarts` 记录每次降幅 |
| **S2 kill -9 续训** | `watch -- python fake_train.py --epochs 10 --self-kill-at 4` | 识别为可恢复，参数不变从最近 ckpt 续训，最终跑完；不出现 batch 调整 |
| **S3 代码错误不反复重启** | `watch -- python fake_train.py --epochs 10 --fail-at 3 --fail-mode type_error` | **只尝试 0 次重启**，直接判不可恢复、推送诊断、退出非零码 |
| **S4 未知错误保守停止** | `--fail-mode unknown_error`（stderr 为无法识别的文本） | 判不可恢复，停止而非反复重启 |
| **S5 batch 下限保护** | `--fail-mode oom`（无条件 OOM）+ `--batch_size 16`，min_value=8 | 减至 8 后不再减小，达 max_retries 后停止，不无限重启 |
| **S6 loss 发散告警** | `--loss-spike-at 4 --loss-spike-ratio 0.5` | cp_2 触发 loss_spike，v0 下动作为 `alert_only`，训练不被打断、跑完 10 epoch |
| **S7 NaN 底线** | `--nan-at 5` | 立即 error 级告警，且该告警不因 advisor 故障被吞掉 |
| **S8 契约缺失降级** | 用一个无 `--resume` 参数的脚本 + 让它崩溃 | 自动恢复关闭，仅告警，不盲目重启 |
| **S9 挂起只告警** | `--hang-at 3`，`no_progress_kill_after: null`（默认） | 超过 `no_progress_timeout` 后推送 warning，**不 kill 训练**，`trigger=hang` 不出现 |
| **S9b 挂起可选重启** | `--hang-at 3`，显式设 `no_progress_kill_after` | kill 并按 `resume_unchanged` 续训，重启记录 `trigger=hang` |
| **S9c 慢训练不误杀** | 每 epoch 耗时略超 `no_progress_timeout` 的正常脚本 | 只告警不动手，训练完整跑完——验证"慢"不被当成"挂" |
| **S10 命令行改写正确性** | `--batch_size 64 --data ./x --seed 42` + 条件 OOM | 重启命令中 `--batch_size` 被替换为 32（只出现一次），`--data`/`--seed` 原样保留 |

S1、S2、S3 就是 v0 的三条验收标准，直接对应 [functional_overview.md](functional_overview.md#v0--先让守护闭环真跑起来)。

## 与真实 GPU 测试的关系

faultbench **不能替代**在真实大模型上的验证，它替代的是"每次改动都要跑一遍真 GPU 训练"这件事：

| 层次 | 手段 | 频率 | 覆盖 |
|------|------|------|------|
| 单元 | 各 cp_ 文档的快速校验 | 每次提交 | 单个方法的行为 |
| **故障注入（本文档）** | faultbench 场景 S1–S10 | 每次提交，秒级，无需 GPU | **故障路径与恢复轨迹** |
| 真实负载 | 一个真会 OOM 的模型（如故意超配的 ResNet/ViT）在真 GPU 上跑 | 里程碑前，人工 | 显存预估精度、真实 OOM 的 stderr 文本形态、长时稳定性 |

真实负载测试仍然必要，尤其是**验证 `_classify_crash` 的 stderr 文本匹配对真实 PyTorch 报错格式有效**——`fake_train.py` 打印的 OOM 文本是人写的，可能与真实 `torch.cuda.OutOfMemoryError` 的输出有差异。这条差异风险要在里程碑前用真 GPU 校准一次，并把真实报错文本样本固化进 faultbench 作为回归用例。

## 目录结构

```
tests/faultbench/
├── fake_train.py            # 可编程失败的假训练脚本（满足 cp_11 契约四项）
├── fake_nvidia_smi.py       # 输出可控 GPU 状态，供 PATH 前置注入
├── scenarios/
│   ├── s01_oom_recover.py   # 每个场景一个文件，断言重启轨迹与最终状态
│   ├── s02_sigkill_resume.py
│   ├── s03_code_error_no_retry.py
│   └── ...
├── fixtures/
│   ├── real_oom_stderr.txt  # 从真实 GPU 采集的 OOM 报错原文（回归用）
│   └── corrupt_ckpt.pth     # 损坏的 checkpoint 样本
└── conftest.py              # 临时目录、PATH 注入、清理
```

每个场景运行在独立临时目录（自己的 `checkpoints/` 与 `logs/`），跑完即清理，互不干扰，可并行。
