# Training Guardian Agent — 纯功能概述

> 让开发者专注于模型与参数，其余交给 Guardian。

---

## 一句话定义

部署在算力端的轻量守护 agent，覆盖训练前预检 → 训练中监控与保护 → 训练后分析与展示的全生命周期。

---

## 核心原则

- **零接触**：guardian 作为独立进程在训练进程之外运行，开发者的训练脚本一行都不用改，不 import、不插回调、不改模型结构
- **确定性优先**：是否异常、能否恢复永远由规则引擎判定，保证零延迟、可离线运行
- **Agent 有限授权**：判定之后"怎么应对/怎么恢复"可选交给 agent，但只能在预设的有限动作集里选择，调用失败或超时强制回退规则默认动作
- **远端友好**：全部运行在算力端，事件推送至本地；同时暴露 MCP 工具层，供 Claude Code / OpenClaw 等外部 agent 客户端接入查看与操作

---

## 架构基线：sidecar-first

guardian 默认以**旁挂进程**（sidecar）形态运行，而不是嵌入训练进程内部：

```
guardian watch --config guardian.yaml -- python train.py --resume-from-latest
  │
  ├─ 训练进程：开发者原样的 train.py，0 行改动
  │
  └─ guardian 进程（独立）
       ├─ 指标来源：tail wandb 本地目录 / tail 日志文件（复用脚本已有的输出）
       ├─ 硬件监控：独立轮询 nvidia-smi，与训练进程完全解耦
       ├─ checkpoint 分析：独立扫描 checkpoints/ 目录
       └─ 干预方式：kill 训练进程 + 用调整后的参数从 checkpoint 重启
```

这个选择直接决定了能力边界，代价必须明说：

| 维度 | sidecar（默认） | 嵌入模式（可选升级） |
|------|-----------------|----------------------|
| 开发者脚本改动 | 0 行 | 需要插回调，非 Lightning 项目还要改循环结构 |
| 异常检测粒度 | 受限于日志/wandb 刷新频率；脚本只按 epoch 打印时就只有 epoch 级 | 真正的 per-step |
| `lower_lr` 等参数干预 | **重启生效**：回滚到最近 checkpoint，用新参数重来 | 进程内直接改 optimizer，下一步立即生效 |
| `skip_batch` | **不可用**（进程外无法跳过某一个 batch） | 可用 |
| NaN 检测延迟 | 秒级（等日志落盘） | 那一步立即 |
| 重启式干预的算力代价 | 浪费掉最近 checkpoint 之后已算的部分，`save_every` 间隔越大浪费越多 | 无 |

**换来的是训练脚本完全不用碰。** 嵌入模式（`GuardianCallback` + per-step 动作集）作为可选的精细化升级保留，当团队愿意接受改脚本、以换取更细粒度和更低延迟的干预时启用，详见 [cp_7.md](cp_7.md) 附录。

### 对训练脚本的两条能力要求

这不是"侵入"，是训练脚本为自身工程质量本来就该具备、guardian 只是复用的能力（完整契约见 [cp_11.md](cp_11.md)）：

1. **可续训**：支持 `--resume` / `--ckpt` 从断点继续。缺失则自动恢复能力关闭，其余功能照常
2. **指标可观测**：往 wandb / tensorboard / 日志文件写指标（哪怕只是 `print(f"step {i} loss {loss}")`）。缺失则实时监控退化为进程级看护（存活 + GPU），无法做 loss 级异常检测

## 功能全景

### 训练前

| 功能 | 做什么 |
|------|--------|
| **资源预检** | 训练启动前自动测量显存占用，列出各 batch size 对应的显存预估，推荐最大安全值，预估总训练时长。预检不通过则阻止启动并给出建议 |
| **参数推荐** | 根据数据集规模、模型结构、硬件条件，推荐学习率、调度策略、数据增强方式等训练参数 |

### 训练中

| 功能 | 做什么 |
|------|--------|
| **实时监控** | 从训练脚本已有的输出通道（wandb / tensorboard / 日志文件）读取 loss、学习率、验证指标；GPU 利用率、显存、温度、功耗由独立进程轮询 nvidia-smi 采集。检测粒度取决于脚本的输出频率 |
| **异常告警** | 自适应检测 loss 发散、停滞、NaN/Inf、GPU 空转、温度过高等异常（规则判定，必然执行），触发终端告警或远程推送（飞书/钉钉/邮件/Telegram），带静默期防刷屏 |
| **异常应对决策** | 异常确认后，配置了 agent 决策层时，在预设的有限动作集里选择应对方式（仅告警/降学习率后重启/回滚到上一 checkpoint）；未配置或调用失败时走规则默认动作。sidecar 模式下参数调整一律经由重启生效，详见 [cp_2.md](cp_2.md) |
| **自动恢复** | 训练中断后自动诊断原因：OOM/断电等可恢复中断自动从最近 checkpoint 续训，代码错误等不可恢复中断停止重试并推送诊断报告（可恢复性判定为规则判定，必然执行）。这也是 sidecar 模式下所有干预动作的统一执行路径，详见 [cp_3.md](cp_3.md) |
| **恢复策略决策** | 可恢复中断确认后，配置了 agent 决策层时，基于历史恢复记录在有限动作集里选择具体策略（如梯度累积而非单纯减小 batch size）；未配置或调用失败时走规则默认策略，详见 [cp_3.md](cp_3.md) |
| **Checkpoint 管理** | 训练脚本自己保存 `cp_{epoch}/`（契约规定必需字段），guardian 在进程外轮询发现新目录后附加快速校验（5% 采样评估）和定期完整校验（全量 + per-class 指标 + 混淆矩阵），维护 top-k 与最优模型引用；不删训练脚本可能正在用的最近几个 checkpoint，详见 [cp_4.md](cp_4.md) |

### 训练后

| 功能 | 做什么 |
|------|--------|
| **日志摘要** | 自动生成一页结构化报告：训练状态、最优模型、最终指标、异常事件汇总（含每次事件是 agent 决策还是规则默认）、资源消耗、学习率调度历史。终端输出 + 文件保存 + 远程推送 |
| **AI 分析报告** | 配置了 agent 决策层时，基于结构化摘要生成自然语言解读（`ai_narrative` 字段），纯输出不影响摘要本身；未配置或调用失败时该字段省略，详见 [cp_5.md](cp_5.md) |
| **Checkpoint 分析** | 扫描所有 checkpoint 的校验结果，生成趋势报告，标注最优模型，支持任意两个 checkpoint 的指标对比 |
| **图片精选** | 按预测置信度、标注质量、类别均衡性自动筛选展示级图片，支持多套精选集（汇报集/难样本集/边界案例集） |
| **成果展示页** | 基于精选图片自动生成可视化展示页面，支持原图/标注/预测对比、多条件筛选、不同 checkpoint 预测结果对比 |

### 跨实验

| 功能 | 做什么 |
|------|--------|
| **实验记录** | 每次训练自动快照完整配置与结果，支持自然语言查询："上次 mAP 最高的 lr 是多少"、"对比实验 #7 和 #12" |
| **管线可视化** | 解析模型结构，生成可交互 HTML 流程图，每个节点可展开查看 tensor shape、参数量、FLOPs，高亮性能瓶颈 |
| **数据质量巡检** | 用训练后的模型反向预测，找出标注与预测严重矛盾的样本，疑似标注错误自动标记 |

## AI 介入层

之前的设计里，AI 层只是规则引擎算完之后的"文本翻译器"——所有决策（异常怎么判、怎么恢复）都由规则引擎定死，AI 只负责把结果转成人话。这不是 agent，是加了一层解释文案。

现在把 AI 层拆成两类，边界画在"这个判断错了会不会威胁训练本身"：

```
┌───────────────────────────────────────────────────┐
│  契约边界层（人定死，agent 不可单方面突破，cp_11）  │
│                                                   │
│  · 训练脚本必需内容（可续训/ckpt格式/指标通道/入口）│
│  · 指标注册表（agent 只能从中选，不能发明）         │
│  · 可调路径白名单 + 幅度上限 + 命令行映射           │
│  · agent 可提议扩展，但需人工审核后才生效           │
└────────────┬──────────────────────────────────────┘
             │ 划定 action_space 与判定口径
┌────────────▼──────────────────────────────────────┐
│  决策层（中层 agent 化，可选，有动作权）             │
│                                                   │
│  · 异常应对方式选择（有限动作集）                   │
│  · 恢复策略选择（有限动作集）                       │
│  · best-model 判定指标选择（注册表内）              │
│  · 训练报告自然语言解读（纯输出，无动作）           │
└────────────┬──────────────────────────────────────┘
             │ AgentAdvisor 统一出入口（cp_9）
             │ 超时/异常/越界 → 强制回退规则默认动作
             │ sidecar 下等待 LLM 不占用训练时间
┌────────────▼──────────────────────────────────────┐
│  规则引擎层（必选，可靠，兜底）                     │
│                                                   │
│  · 滑动窗口异常检测（判定"是不是"）                 │
│  · 崩溃类型分类（判定"能不能恢复"）                 │
│  · 显存测量与线性回归                              │
│  · Checkpoint 发现/校验/清理                       │
│  · 告警静默期管理                                  │
│  · 进程看护与重启（sidecar 唯一干预手段）           │
└────────────┬──────────────────────────────────────┘
             │ 暴露为标准工具（读 + 受限写）
┌────────────▼──────────────────────────────────────┐
│  MCP 工具层（外部 agent 接入，cp_10）               │
│                                                   │
│  · Claude Code / OpenClaw 等客户端                  │
│    可查看指标、checkpoint、告警历史、契约状态        │
│  · 受限写：触发恢复/带参重启/审批契约提议            │
└───────────────────────────────────────────────────┘
```

关键区别：
- **"是不是异常"“能不能恢复”永远是规则引擎判定**，不过一遍 LLM。这类判断需要零延迟、确定性、能离线跑——训练不能等一次网络请求才知道要不要救。
- **"异常发生后怎么应对"“选哪种恢复策略”“用什么指标衡量好坏”交给 agent**，但只能在契约层预先定义的有限动作集/注册表里选，不能自由发挥（比如不能自己发明一个指标的算法，也不能去调白名单外的参数）。
- **agent 调用一律经过 AgentAdvisor**（见 [cp_9.md](cp_9.md)），超时或报错直接回退到该决策点原本的规则默认动作，训练不会因为 LLM 不可用而卡住或出错。
- **agent 想让"自己下次能选的范围"变大，只能提议**（见 [cp_11.md](cp_11.md)），提议不生效、当次仍走默认值，人工审核通过后才写入正式注册表。扩大 agent 的自由度这件事本身，不交给 agent 决定。
- **MCP 工具层**（见 [cp_10.md](cp_10.md)）把上面几层的能力暴露给外部 agent 客户端，读操作不受限，写操作只开放明确列入白名单的动作，且用 MCP 原生 annotations 标注风险等级。

契约层规定"能选什么"，规则引擎保证"选不出来也不会崩"，决策层让"怎么办"从死板规则变成有上下文推理的判断，MCP 层让整套系统可以被其他 agent 生态接入使用。四层的共同不变式：**agent 的自由度永远是人显式授予的，且任何一层失效都退回上一层的确定性行为。**

## 部署方式

| 模式 | 适用场景 | 集成成本 |
|------|----------|----------|
| **守护模式（默认）** | `guardian watch -- python train.py`，包装训练命令做进程级守护，训练脚本 0 行改动 | 最低（只需脚本可续训 + 有指标输出） |
| **远程集群模式** | SLURM/PBS 集群，事件推送至本地；同为 sidecar 形态 | 中 |
| **嵌入模式（可选升级）** | 需要 per-step 检测或进程内即时干预（`skip_batch`、不重启改 lr）时才启用，需在训练脚本插回调 | 中（要改训练脚本，非 Lightning 项目还要改循环结构） |
| **+ Agent 决策层** | 在以上任一模式基础上叠加，`pip install -r requirements-core.txt` 即含此能力，配置 API key 即启用 | 低（未配置自动降级为纯规则，不影响原有模式，且不需要额外装包） |
| **+ MCP 接入** | 独立于训练模式，`pip install -r requirements-mcp.txt` 后 `run.py serve` 或 `--with-mcp` 启动，供 Claude Code / OpenClaw 等外部 agent 连接；可以在训练已经在跑的情况下随时补挂，无需重启 | 低（只读工具默认开放，写工具默认关闭；未装 `mcp` 包或启动失败只降级为不可用，绝不影响训练主循环，详见 [cp_10.md](cp_10.md)） |

默认路径是**守护模式**：`guardian watch -- python train.py`，训练脚本原样不动。嵌入模式不是"更好的接入方式"，而是"愿意改脚本换取更细粒度干预"时的升级项——集成成本比守护模式更高，不是更低。

Agent 决策层和 MCP 接入都是叠加在原有部署模式之上的能力开关，不是新的部署模式——服务器只跑训练规则引擎、只跑训练+决策层、只跑训练+MCP 接入、三者全开，都是同一套代码的不同配置组合。**两者的依赖也物理隔离**（[requirements.md](requirements.md)）：轻量远程部署只装 `requirements-core.txt` 就能获得完整的 agent 决策能力，MCP 相关依赖完全不会出现在这类部署里；什么时候需要被外部 agent 客户端接入，什么时候再补装 `requirements-mcp.txt`，是一个可以推迟到训练已经在跑之后再做的决定，不是部署当下必须敲定的事。

## 优先级

### v0 — 先让守护闭环真跑起来

目标：一个真实会崩的训练任务，被守护、被救回来、有摘要。**这一档不含任何 agent 与 MCP 能力**，全部纯规则。

| 模块 | 内容 |
|------|------|
| cp_3 | 进程看护 + 崩溃分类 + 从 checkpoint 重启 + 命令行改写执行层（sidecar 核心） |
| cp_12 | 故障注入测试装置（**与 cp_3 同步开发**，否则下面的验收标准无法验证） |
| cp_2 | 指标通道 tail + 规则异常检测（应对动作只到 `alert_only`） |
| cp_6 | 告警推送 |
| cp_4 | checkpoint 轮询发现 + 校验 + best/top-k |
| cp_5 | 结构化摘要（不含 `ai_narrative`） |
| cp_11 | 仅硬性契约四项的校验与降级（不含注册表/白名单/提议流程） |

v0 的验收不是"MNIST 跑通"，而是三条可执行的断言（对应 [cp_12.md](cp_12.md) 的 S1/S2/S3 场景）：

1. **OOM 能救回来**：条件性 OOM 的脚本，guardian 减 batch 后**训练跑完全部 epoch**——不是"重启了"就算，重启后继续 OOM 不叫救回来
2. **`kill -9` 能续训**：参数不变从最近 checkpoint 接上，最终跑完
3. **代码错误不反复重启**：`TypeError` 触发 **0 次**重启，直接判不可恢复并推送诊断

这三条用 MNIST 一条都验证不了（见 [cp_7.md](cp_7.md) 测试用例局限），必须靠 cp_12 的故障注入装置。**"能跑起来"不是 v0 完成，"能救回来"才是。**

### v2 — 尚未设计的功能（当前无 cp_ 文档）

功能全景里列了、但**还没有对应设计文档**的部分，先记在这里，避免"文档承诺的范围"与"设计覆盖的范围"对不上：

| 功能 | 状态 |
|------|------|
| 参数推荐（训练前推荐 lr / 调度 / 增强） | 无 cp_ 文档；风险低（纯建议、不自动生效），适合作为 agent 参与的第一块扩展地 |
| 图片精选、成果展示页 | 无 cp_ 文档；纯训练后产出，与守护闭环解耦 |
| 实验记录（跨实验 NL 查询） | 无 cp_ 文档；只读推理，天然适合挂在 cp_10 的 MCP 工具层上 |
| 管线可视化 | 无 cp_ 文档；需要 `buildable_entry` 契约 |
| 数据质量巡检 | 无 cp_ 文档；只读推理，零训练风险 |
| 推理测试助手 | 无 cp_ 文档 |

这几项要么补设计文档，要么明确从"功能全景"降级为"未来考虑"——两者都可以，但不该停在"全景里写了、设计里没有"的状态。

排期逻辑：**先把"训练崩了能救回来"这件事做实（v0 全纯规则），再让"怎么救"变聪明（v1 引入 agent），最后才是训练之外的产出与展示（v2）。** agent 决策层和 MCP 工具层虽然是这次改造的核心目标，但它们的价值建立在 v0 的动作集已经被真实故障验证过之上——动作本身还没验证过能不能救回训练，就先让 LLM 来选用哪个动作，顺序是反的。
